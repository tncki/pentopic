01做出来的东西

23 个工具、四语界面、6 种导出格式 —— 起点只是「复刻」两个字。

竖排双列工具栏，23 个工具。指针排在最前 —— 它是默认工具，因为刚冻结屏幕时， 人最可能先做的是看看、挪一挪已有的标记，而不是立刻落笔。

工具栏、颜色、形状位置全都可以右键改，整套布局能导出成 JSON。

原版 Pointofix 有 16 个工具。多出来的部分大多是 「用起来才发现需要」的：打码、聚焦、序号、标尺、吸管、选择与排列。

02人和 AI 各自做了什么

这份分工不是事先设计的，是十天后回看总结出来的。它可能是全文最有参考价值的部分。

人给方向与验收，AI 给实现与验证。中间的往返是关键。

11 个真实缺陷，全部由人实机发现 —— AI 的 256 项自检一个都没提前发现。
原因不神秘：AI 写的测试，测的是它自己理解的规格。规格理解错了，测试再全也测不出来。

03深挖一个：撤销为什么突然不管用了

这是所有缺陷里唯一一个「架构性」的 —— 改起来动的是数据模型，不是某一处逻辑。

用户报告：选中几条笔画删除，按 ⌘Z 没反应 —— 而且更糟，撤销会把别的笔画弹掉。

教训：当撤销建立在「操作是追加」的假设上时，任何"修改已有数据"的功能都会悄悄失去撤销能力。 修删除是不够的 —— 对齐、移动、组合其实也全都不可撤销，用户只是先撞上删除。

04四类缺陷

把它们分类，是因为类型会重复。认出来，才能提前防住。

类型 A · 架构性

代码看起来对，错的是数据模型

撤销只能表示"追加"删除、对齐、移动、组合全部不可撤销（详见上一节）
选择框无条件绘制切走工具后虚线框还赖在屏幕上。排查时又发现选中计数用的是 id 数量而非实际存在的笔画 —— 撤销后留下悬空引用，删除会对着不存在的对象操作。
窗口钳制只判断"是否完全不相交"工具栏长得超出屏幕时，底部被切掉，顶部拖动柄也够不到。
类型 B · API 陷阱

文档不写，推导推不出，只有实测才发现

.useOpticalBounds 不是墨迹包围盒它返回的是整个行盒。要用 .useGlyphPathBounds。
NSColor.whiteComponent 会抛异常对不兼容的色彩空间不是返回默认值，是抛异常 —— 测试直接崩了。
类型 C · 可发现性

功能存在，但用户用不到 —— 等于不存在

用户"重新发明"了一个已存在的功能他建议"加一个能移动笔画的指针工具" —— 而那个工具上一轮刚做完，只是工具栏里根本没有按钮：一次字符串替换静默失败，没有编译错误、没有测试失败。
工具栏只能从约 9px 的空隙拖动拖动区确实存在（探测视图层级：66×18），但 SwiftUI 的 Text 默认拦截点击，把 66px 里只剩 Spacer 那一小条。
类型 D · AI 自身的失误

不是能力问题，是流程问题

编造了一个不存在的原作者姓名写进了文档。全站爬取后证明不存在 —— 唯一匹配是 "Svenska"（瑞典语）。当时授权邮件正准备发出去。
同一个浮窗收尾错误犯了两次放大镜漏了一次，后来的取色面板又漏了一次。
改默认值忘了它是持久化的上一版已把旧值写进 UserDefaults —— 表现是「我改了代码，行为却没变」。

最值得单独说的一个

AI 失误 · 诊断工具自己出错

我的过滤器把警告当成了错误，带偏一整轮

困境CI 构建失败，但 Actions 日志需要管理员权限才能下载。
绕道让流水线把错误行作为 annotation 发出来 —— 那是公开 API 能读到的。
失误过滤模式含 error，匹配到了警告文本里的 "this is an error in the Swift 6 language mode"。于是警告看起来像编译错误。
后果我照着这些"错误"去清理 Swift 6 并发问题，加了一批 @MainActor，把原本正常的构建搞坏了。收手、撤销、改用严格模式重新取证据后才发现：本地真正的编译错误是 0 个。

诊断工具自己出错时，比没有诊断更危险 —— 它会让你在错误的方向上自信地走很远。 当我根据"工具的输出"去做大范围改动时，先花一步验证这个输出是什么意思：代价 1 分钟，而误判的代价是整轮返工。

05测试是怎么长起来的

自检项数：45 → 256。其中相当一部分是历史缺陷的墓碑 —— 每修一个，就补一条防回归断言。

数量本身不重要，写法才重要。下面五条都是踩坑换来的：

原则反面教材（真实发生过）现在怎么做
测试必须能失败 —— 断言浮窗被收起前，先断言"收起前确实有浮窗"，否则那句断言永远为真
差分 + 对照组 只看"画面变了"分不清是功能生效还是随机重绘 切工具画面变 222 像素；且两个都不带选择的工具之间切换必须 0 像素变化
验证身份而非数量 别把"红色包围盒"当圆形定位，那给出过一个假通过的 0.0 偏差 删中间那条再撤销，断言恢复的就是它（坐标 500），而不是"数量变成 3"
底图必须确定性 打码测试依赖真实屏幕，同一台机器跑出 0.93 和 4.21 两种结果 改用合成棋盘图 → 稳定在 42.33 → 0.70
构建产物也要验 使用手册是构建时生成的，转换失败只有一行警告 自检直接检查打包后的 HTML，而不是源码

07可复用的做法

1. 让 AI 写提交信息，而且要写「为什么」

45 次提交，信息普遍长这样：

「撤销栈就是笔画数组本身，removeLast() 只能表示追加。删除改的是数组中间， 所以撤销会弹掉另一条笔画 —— 删除因此完全不可撤销。」

这类信息三个月后比代码本身更有价值。让 AI 把推理过程写进提交信息，是性价比最高的一条。

2. 每次修复都补一条防回归测试

不是"修完就算"，而是"修完并锁死"。到发布时，256 项自检里相当一部分是历史缺陷的墓碑。

3. 人能上手做的事，不要让 AI 代替判断

11 个缺陷全部来自人的实机使用。AI 写的测试测的是它自己理解的规格 —— 规格错了，测试再全也测不出来。

4. 对外沟通的每一句都要落到事实

授权邮件里关于仓库可见性、署名方式、是否已发布的措辞都逐字核对过。对方说的是 „keine Einwände"（不反对），我在 README、NOTICE、邮件里都写"不反对"， 没有一处升级成"授权合作"或"官方认可"。

5. 发布前扫描全部历史，不只是当前文件

我从当前文件里删掉了个人邮箱，但三个历史版本仍有它。仓库公开意味着全部历史公开。 扫描要覆盖 git rev-list --objects --all 的每个 blob。

08这套方法的边界

它适合它不适合
规格相对明确、可本地验证的工具类软件需求本身还在探索、连"好不好"都难判断的产品
有自动化测试兜底、能快速迭代的场景错了代价极高、无法回滚的领域（资金、医疗、生产环境）
人能上手实测、并且愿意实测没有验证条件，只能"相信它写对了"

最有效的用法不是"让 AI 写代码"，而是"让 AI 写代码，然后你认真用它"。
这个项目里 AI 产出的质量，很大程度上取决于用户愿意花多少时间实测和追问。 那 11 个缺陷、那些"重新发明已有功能"的建议 —— 每一次追问都直接把项目往正确方向推了一步。
