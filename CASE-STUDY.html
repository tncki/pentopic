一、做了什么

PentoPic 是一个 macOS 屏幕标注工具：按一下热键，屏幕冻结成画板，直接在画面上用画笔、箭头、图形、文字、打码、聚焦讲解，然后保存或分享。

起点是一句需求：「把 pointofix.de 复刻成 mac 版本的软件」。终点不只是复刻 —— 发布版本有 23 个工具（原版 16 个），并拿到了原作者的书面许可。

维度结果
仓库github.com/tncki/pentopic · MIT · Public
发布v1.0.0 · 通用二进制（Intel + Apple Silicon）· 1.4 MB
技术纯 Swift + AppKit / SwiftUI / ScreenCaptureKit，零第三方依赖
构建只用 Command Line Tools，不需要完整 Xcode
授权Pointofix 著作权人书面表示不反对发布（存档于仓库）

二、人和 AI 各自做了什么

这份分工不是事先设计的，是十天后回看总结出来的。它可能是这个案例里最有参考价值的部分。

人AI
需求 全部。包括原版行为对齐、以及后期 6 项功能扩展的取舍 把需求翻译成可执行的技术方案，列出选项与代价
交互设计 关键决策全部来自人：主工具 + 修饰键临时借用的模型、打码要真读底图、撤销要覆盖全部编辑 实现，并在实现中暴露边界情况
测试 11 个真实缺陷全部由人实机发现。这是价值最高的输入 270 项自动化自检，覆盖像素级、状态机、导出格式
构建与验证 决定发布节奏、签名方案、是否公证 写构建脚本、跑验证、打包、核对产物校验和
文档 校对措辞（尤其对外的授权邮件） 撰写，含使用手册、变更日志、发布说明、许可存档

一个稳定的模式：人负责「做什么和为什么」，AI 负责「怎么做」，而人继续用实机测试来验收。AI 自己写的测试，无法替代人上手用一遍 —— 下面第二节的案例会反复证明这一点。

三、六个真实案例

下面每一条都真实发生过，按性质分类。它们的价值不在于"AI 出错了"，而在于这些错误有固定的类型 —— 认出来，就能提前防住。

类型 A · 架构性缺陷

代码"看起来对"，局部逻辑也没错，错的是数据模型或假设。

架构

「删除之后，撤销就不管用了」

现象
选中几条笔画删除，按 ⌘Z 没反应 —— 而且更糟：撤销会把别的笔画弹掉。
根因
撤销栈就是笔画数组本身，撤销实现是 strokes.removeLast()。这只表示「追加」一种操作。而删除改的是数组中间。
影响面
不光是删除 —— 对齐、移动、组合、层级全都不可撤销，因为它们改的都是中间元素。用户只是先撞上删除。
修法
改成快照式撤销：每次修改前存整份笔画。拖动这类连续操作只在开始时记一次。
教训：当撤销/重做建立在"操作是追加"的假设上时，任何"修改已有数据"的功能都会悄悄失去撤销能力。先问数据结构能不能表示所有操作，再写功能。
架构

「选择框切了工具还赖在屏幕上」

根因
选择框无条件绘制，完全不看当前是哪个工具。
连带发现
排查时发现 selectedCount 用的是 selection.count —— 统计的是 id 数量，不是实际存在的笔画。撤销后留下悬空引用，计数虚高，删除会对着不存在的对象操作。
教训：一个视觉 bug 常常牵出一个状态管理 bug。修表面的同时，问一句"这个状态还有谁在用、用得对不对"。

类型 B · API 陷阱

文档不会告诉你，推导也推不出来，只有渲染出来看一眼才会发现。

API

「序号数字不在圆的中心」

现象
序号标在圆里偏下，直径越大越明显，160pt 时数字直接溢出圆外。
根因（两层）
① 基线定位公式 center.y + height/2 - minY 我当时以为等价于包围盒中点 midY —— 代数上不等价，它把基线压到了圆心下方约 28pt。
② 更隐蔽的：我用的 .useOpticalBounds 返回的根本不是墨迹包围盒，而是整个行盒（含升降部、完整前进宽度）。正确的是 .useGlyphPathBounds。
怎么发现的
把序号渲染成 PNG 用眼睛看 —— 一眼就看出偏下。纸面推导在两个环节上都是"对的"。
教训：几何/排版类代码不要靠推导验收。渲染出来看，或者写像素级断言。我最初写的测试用「红色像素包围盒」定位圆形，把整个采样框都算进去了，给出了一个假通过的 0.0 偏差。
API

两行代码，一个崩溃一个发暗

NSColor.whiteComponent
对不兼容的色彩空间抛异常（不是返回默认值）。我的测试直接崩了。必须先 usingColorSpace(.sRGB)。
CIGaussianBlur
不先 .clampedToExtent() 就裁回原尺寸，边缘采样不到内容会发暗 —— 打码区四周出现一圈灰边。这是该 API 最经典的坑。
教训：Objective-C 时代的 API 用异常而非返回值报错。涉及色彩空间、索引、范围时，假设它会抛。

类型 C · 可发现性

功能存在，但用户用不到 —— 等于不存在。

可发现性

「建议加一个能移动笔画的指针工具」

背景
用户提了这条建议。而那个工具上一轮刚做完 —— 只是它在工具栏里根本没有按钮。
根因
一次字符串替换静默失败，导致 toolRows 里少了那一行。没有编译错误，没有测试失败。工具只能靠快捷键 V 调用。
教训：用户"重新发明"一个已有功能，是可发现性失败的铁证。补了一个覆盖性测试：工具栏必须包含全部 23 个工具，且指针排在最前。这条测试如果早就在，那次失败会立刻暴露。
可发现性

「鼠标无法移动工具栏」

根因
拖动区确实存在（探测视图层级：66×18），但 SwiftUI 的 Text 默认是命中目标，盖住了它。整个标题栏只剩 Spacer 那 约 9px 的空隙能按到 —— 跟不能拖没区别。
教训：「控件存在」不等于「可操作」。验证交互时要量可点击区域，而不是确认控件在层级里。

类型 D · AI 自身的失误

这一类最值得单独说，因为它不是能力问题，而是流程问题。

AI 失误

编造了一个不存在的原作者姓名

经过
我在文档里写了原作者是「Dipl.-Ing. Sven Frotscher」。这个名字是我编的 —— 网站全站爬取后证明不存在，唯一匹配是 "Svenska"（瑞典语）这个词。
怎么发现的
用户要求核对，我去逐页抓取验证，才确认是虚构。
教训：AI 会流畅地编造看起来合理的事实，而且它自己毫无察觉。凡是可核查的事实（人名、版本号、API 存在性、许可证），都必须落到可验证的来源。这条在对外沟通里尤其致命 —— 当时的授权邮件正准备发出去。
AI 失误

诊断工具自己出错，把我带偏了一整轮

背景
CI 构建失败，但 Actions 日志需要管理员权限才能下载。于是我让流水线把错误行作为 annotation 发出来 —— 那是公开 API 能读到的。
失误
我的过滤模式包含 error，匹配到了警告文本里的 "this is an error in the Swift 6 language mode"。于是警告看起来像编译错误。
后果
我照着这些"错误"去清理 Swift 6 并发问题，加了一批 @MainActor，结果把原本正常的常规构建搞坏了。收手、撤销、改用严格模式重新取证据后才发现：本地真正的编译错误是 0 个。
教训：诊断工具本身也需要被怀疑。当我根据"工具的输出"去做大范围改动时，先花一步验证这个输出是什么意思 —— 用严格模式重新匹配一次，代价是 1 分钟，而误判的代价是整轮返工。
AI 失误

改默认值时忘了设置是持久化的

经过
把「打开会话时的默认工具」从"指针"改成"画笔"。但上一版已经把旧默认值写进了 UserDefaults —— 不改就完全不起作用。表现是「我改了代码，行为却没变」。
修法
加一次性迁移：识别出"这是旧默认值而非用户主动选择"，丢弃它；迁移之后用户的选择仍然被保留。
教训：任何持久化的默认值一旦发布，就等于承诺。改默认值之前先想：老用户读到的是什么？需要迁移吗？

数量本身不重要。真正起作用的是测试的写法 —— 下面这五条都是踩坑之后总结出来的：

原则为什么具体做法
测试必须能失败 一个不会失败的测试等于没有测试 断言前先确认"前提成立"。比如验证浮窗被收起前，先断言"收起前确实有浮窗"
用差分，配对照组 只看"变化了"分不清是功能生效还是随机重绘 切换工具后画面变了 222 像素；两个都不带选择的工具之间切换必须 0 像素变化
验证身份，不只是数量 数量对不代表恢复对了 删中间那条再撤销，断言恢复的就是它（坐标 500），而不是"数量变成 3"
底图必须确定性 依赖真实屏幕的测试会随机波动，让人误以为偶发 打码测试改成合成棋盘图 —— 同一台机器上原本会跑出 0.93 和 4.21 两种结果
构建产物也要验 构建脚本里的转换失败可能只是一行警告 使用手册是构建时生成的 —— 自检直接检查打包后的 HTML，而不只是源码

六、可复用的做法

1. 让 AI 写提交信息，而且要写「为什么」

45 次提交，信息普遍长这样：

「撤销栈就是笔画数组本身，removeLast() 只能表示追加。删除改的是数组中间，所以撤销会弹掉另一条笔画 —— 删除因此完全不可撤销。」

这类信息在三个月后比代码本身更有价值。让 AI 把它的推理过程写进提交信息，是这个流程里性价比最高的一条。

2. 每次修复都补一条防回归测试

不是"修完就算"，而是"修完并锁死"。上面 11 个缺陷，每一个都留下了对应的断言。到发布时，270 项自检里相当一部分是历史缺陷的墓碑。

3. 人能上手做的事，不要让 AI 代替判断

11 个缺陷全部来自人的实机使用，AI 的自检一个都没提前发现。原因不神秘：AI 写的测试，测的是它自己理解的规格。规格理解错了，测试再全也测不出来。

4. 对外沟通的每一句都要落到事实

授权邮件里关于仓库可见性、署名方式、是否已发布的措辞，都被逐字核对过。AI 起草 + 人校准措辞 是对外文本的稳妥组合 —— 它写得快，但"有没有说过头"必须人来判断。

5. 发布前扫描全部历史，不只是当前文件

我从当前文件里删掉了个人邮箱，但三个历史版本仍有它。仓库公开意味着全部历史公开。扫描工具要覆盖 git rev-list --objects --all 的每个 blob，而不是 git grep 当前树。

七、这套方法的边界

需要说清楚几件事，否则这个案例会被误读：

它适合它不适合
规格相对明确、可本地验证的工具类软件 需求本身还在探索、连"好不好"都难以判断的产品
有自动化测试兜底、能快速迭代的场景 错了代价极高、无法回滚的领域（资金、医疗、生产环境）
人能上手实测、并且愿意实测 没有验证条件，只能"相信它写对了"

这个项目里 AI 产出的代码质量，很大程度上取决于用户愿意花多少时间实测和追问。 那 11 个缺陷、那些"重新发明已有功能"的建议 —— 每一次追问都直接把项目往正确方向推了一步。

最有效的用法不是"让 AI 写代码"，而是"让 AI 写代码，然后你认真用它"。
